# 初読評価

この評価は candidate.json の本文と参照一覧だけに基づく。リンク先のコードは読んでいないため、実装との一致は判断していない。

## 1. 最初のコード参照に入る前の文脈

最初の参照より前に読めるのは、実質的に「最後の画面を閉じた直後に、もう一度 `rvw open` したとする。旧プロセスは終了処理に入り、新しい依頼を受け付けなくなっているかもしれない」という状況である。

ここから述べられるのは、画面を閉じてすぐ再度開こうとすると、終了中の旧プロセスに依頼できない時間がありそうだ、ということまでだった。画面とプロセスがどう結びつくか、何が起動を排他制御するか、再試行でどの状態を変えられるかという仕組みは、まだ述べられない。コードを開く目的も「この間に再度開くとどうなるかを見る」までは推測できるが、「接続再試行だけでは進めないので、ロック取得も毎回試すことを確かめる」とは言えない。

参照名の「起動先を決めるループ」を読み、その後の「各周回でまず自分が起動できるか試し、できなければ既存プロセスに画面を開くよう頼む」まで進めると、開く理由が具体化する。さらに次段落のローカル HTTP サーバーとロックの説明を読むと、その二択が必要な理由も理解できる。したがって入口が無意味なのではなく、最初のコード参照を開く判断に必要な説明が、その参照より後ろに置かれている。

未解決なのは、最後の画面を閉じると常に終了処理が始まるのか、条件付きなのかである。本文は「かもしれない」としており、この例が成立する条件の提示としては読めるが、画面数から終了への規則は分からない。

## 2. 一つのケースとして再構成できた状態変化

中心のケースは「終了しかけた旧プロセスと同じデータベースを、新しい open が引き継いで画面を開こうとする」で一貫している。本文から組み立てられる順序は次のとおり。

1. 旧プロセスは画面を提供していた。プロセス内に HTTP サーバーと Runtime があり、Runtime はデータベースやサービスをまとめる。旧側が同じデータベース向けのロックを持っている。
2. 最後の画面を閉じた直後を、この例の出発点とする。旧側は終了処理に入り、socket の受付停止、HTTP の終了、Runtime とデータベースの終了、ロック解放の順で進む。受付が止まってもロックは残る期間がある。
3. 新しい CLI は通常、まず既存プロセスへ依頼する。本文が明示するのは、ここで停止通知を受けた場合に worker を作り、ループへ進む経路である。
4. 旧ロックが残る間に新側が取得を試みても、生存中の PID のロックがあるため取得できない。取得できなかった socket オブジェクトは自動で取得を再開せず、CLI が `close()` する。
5. 新側は既存プロセスへ `viewer.open` を送ろうとする。利用不可、または指定された停止通知なら 50 ms 待ち、期限前なら再び開始操作とロック取得を試す。
6. その間に旧側が Runtime とデータベースを閉じ、ロックを解放する。新側の次の取得が成功すると、ループは `owned` を返す。
7. `owned` を受けた worker が `runtimeFactory()` と `startServer()` へ進み、次のサーバーを作る。既存 URL を得た場合の `reused` はこの初期化より前に戻る。

特に「`Runtime.close()` はデータベースを閉じるので、受付を止めてからデータベースを閉じ終えるまでの間にもロックは残る」が、単なる接続失敗と起動許可の違いを一つの時間区間に結びつけている。「取得できなかった socket オブジェクトが後で勝手に起動側になるわけではない」も、同じ候補の状態変化と、新しい候補による次の試行を混同せず読む助けになる。

ただし、次の箇所は本文だけでは埋まらない。

- 冒頭はすでに受付が止まっている可能性を扱う一方、通常 CLI の説明で明示される worker への移行条件は「停止通知」である。最初の直接依頼で接続自体ができず `available: false` となった場合も worker へ進むのかは、書かれていない。上の 3 から 4 へ常に進めるとは断定できなかった。
- worker が別の OS プロセスなのか、既存プロセス内の実行単位なのかは説明されない。「通常の CLI」と「その worker」は区別されているが、新側の PID と起動操作の主体まで固定するには推測が必要になる。
- 7 の後、新しく作られた URL がどこへ戻り、誰が画面を開くのかは描かれない。サーバー起動の引き継ぎまでをケースの終点とすれば成立するが、ユーザーがもう一度画面を見るところまで完結したとは言えない。

## 3. コード参照を開く理由

参照の多くには、確認したい因果関係が直前または直後にある。`shutdown` と `socket-release` は「接続できないのに起動してはいけない期間がなぜあるか」、`lock-acquire` は「新側が何に阻まれるか」、`runtime-socket` は「誰が再取得を始めるか」、`worker-result` は「取得できたことが実際の新規初期化につながるか」を確認する入口になっている。ファイル名を順番に紹介しているだけではない。

`stopping-error` → `stopping-guard` → `uncertain-result` も、待ってよいエラーをどう識別し、何をそこから除くか、という読書目的を保っている。実 socket テストの「旧側が受付を止め、新側の最初の取得失敗を待ち、その後に旧ロックを解放する」は、冒頭の条件を作る具体的な手順として読める。

一方、最初の `handoff` は前述のとおり目的の説明が後置されている。`runtime-object` も、参照時点では「データベースやサービスをまとめる」という説明に留まり、直後の段落で初めて close とロック解放順の理解に必要だったと分かる。これらは接続自体が欠けるというより、コードを開く理由を後から回収する構成である。

## 4. モジュール・データ形式・非同期処理の受け渡し

明確に追えたのは、CLI の開始操作から socket のファイルロック取得へ、取得結果から CLI の分岐へ、`owned` から worker の Runtime/HTTP 初期化へ、というつながりである。`owned` と `reused` の意味が先に定義され、URL が返る場合と新規初期化に進む場合を区別できる。

例外についても、発生側の具体的なデータ「`PROCESS_FAILED` に `details.reason: "runtime-stopping"`」と、受信側の検査「RvwError、code、reason の全て」が示されるため、単に『停止を処理する』より追いやすい。

ただし、次の受け渡しには空白がある。

- CLI が内部 socket 操作を送ることと、「HTTP サーバー側の予約操作」が停止エラーを作ることの間に、実際の呼び出しが示されない。socket 側から HTTP リクエストを出すのか、同じプロセス内の関数を呼ぶのかは分からない。参照一覧の `runtime-socket` に「handler を待って viewer.open を呼び」とあるが、handler の設定元と予約操作との関係は本文に接続されていない。
- プロセス間で伝わるエラー情報が、受信側でどのように `RvwError` になるかは分からない。一般的な socket 通信の知識から直列化・復元を想像できても、それは候補本文の説明ではない。
- 同じデータベース向けのロックという説明はあるが、新しい open のデータベース指定がどうロックのパスや送信内容に反映されるかは分からない。後に出る `database-mismatch` が何と何を比較した結果なのかも特定できない。

非同期の順序は比較的よく限定されている。「50 ms は次の試行までの待機量」「各処理の完了後に期限を検査する」は、処理時間と待機時間を混同しないために有用である。図の矢印がプロセス間の絶対的な時刻を表さないとの断りも適切。ただし各接続操作そのものの上限時間までは示されず、全体の終了時刻を本文だけで計算することはできない。

## 5. 条件を変えた場合として読める分岐

分岐は、同じ再度 open する依頼について条件を変えたものとしておおむね読める。

- 旧側が利用可能な URL を返せるなら `reused` となり、新側で Runtime/HTTP を作らない。
- 旧側のロック解放が間に合えば、新側は再取得して `owned` になる。
- 取得できず利用可能な URL も得られないまま期限に達すれば `PROCESS_TIMEOUT` になる。
- 利用不可でも理由が `database-mismatch` なら待機に進まない。
- 停止理由と一致する例外だけ待機へ進み、その他の例外や送信後の結果不明は投げ直す。

「任意の失敗を表す名前ではない」として停止通知の中身を示す段落は、分岐条件を具体化している。一方、停止通知を返せる時点と、socket 受付がすでに止まっていて通知を返せない時点の境界は明示されない。同じ終了過程のどの時点ならどちらを観測するかは、読者が組み立てる必要がある。

末尾の「PR の取得に時間がかかる場合」は、今回の中心ケースの条件を変えた説明としては弱い。PR、予約、接続待ち期限がそこで初めてまとまって登場し、120,000 ms の起動期限とは別の時計なのか、その予約が画面や終了処理とどう関係するのかは解かれない。次の調査先の提示としては読めるが、今回の説明内で理解できる分岐ではない。

## 6. 変更条件から予測できることと確認先

同じ旧プロセスの終了中でも、新側が送った依頼の処理結果を確定できなくなった場合を考える。本文からの予測は、これを停止通知として 50 ms 後に再実行せず、例外を投げ直す、である。理由は「この停止判定に一致しない」と明記され、停止通知以外の例外は投げ直すとされるからである。

確認する順序は、`uncertain-result`（`src/server/agent-socket.ts` 416–427 行）でその例外のデータを見て、`stopping-guard`（`src/cli/main.ts` 237–241 行）で識別条件と比較し、`handoff`（同 594–633 行）で一致しない例外が投げ直される分岐を見る。この予測と確認先は本文だけから選べる。ただし、結果不明を生む具体的な通信イベントと、相手側で依頼が実行済みかどうかは本文からは予測しない。

## 7. 具体性と長さ

説明を支えているのは抽象的な名称より、PID を書いたファイルをリンクすること、socket 候補を閉じること、Runtime.close でデータベースを閉じること、URL と取得結果を返すこと、reason を照合すること、二回目の開始操作を期待すること、といった観測可能な操作である。特に終了順序と再取得の関係は、長さを使って有用なつながりを作っている。

図は各周回の分岐をまとめるのに役立つが、それだけでは旧側のデータベース終了とロック解放は追えない。その情報を前後の文章が補うので、本文と図にはそれぞれ必要な内容がある。二つのテスト参照も、終了順序と実際のロック引き継ぎという異なる確認点を示しており、単なる重複とは感じない。

長さに対して最も回収が薄いのは末尾の PR 取得・予約・別の時計への予告である。それを読む分の注意を、通常 CLI の接続不可から worker へ進む条件や、socket の viewer.open が予約操作へ届く経路に使う方が、この一例の理解を閉じやすい。全体として中心の引き継ぎは再構成できるが、最初の参照前の仕組みの提示と、通信・例外・worker の境界を完全に追うところには推測が残った。
