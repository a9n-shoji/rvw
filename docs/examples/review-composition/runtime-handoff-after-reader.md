# 初読評価

評価対象は指定された `candidate.json` の本文・図・参照一覧だけです。参照先のコードや実行結果は確認していません。以下は説明から何を理解でき、どこが未確定のままかという評価です。

## 最初のコード参照を開く前

冒頭の二段落だけで、次のことは説明できます。

- 仕組みの外形：`rvw open` は GitHub の PR をローカルの HTTP 画面で開き、SQLite と HTTP サーバーを持つ既存プロセスを再利用する。ブラウザー文書を viewer、そのプロセスを runtime と呼ぶ。
- 今回の状況：最後の画面を閉じた後の終了猶予中に、次の open が届く。受付可能で、database は同じ、port は衝突せず、時間のかかる PR 取得とその後の接続は成功する。
- 読む目的：「PR を調べる時間で『次のブラウザーを待つ時間』を使い切らない仕組み」を確認すること。

したがって、最初の「通常の open の入口」を開く理由は、次の open が既存プロセスへどう到達し、ブラウザーを開くまでにどんな処理が挟まるかを確認することだと理解できます。ただし、参照前の時点では、接続待ち時間を守る具体策が予約の二段階化であることはまだ言えません。導入として問いは明確ですが、解決策まで先に示す導入ではありません。

「ブラウザーの画面がなくなると終了します」と、次段落の「終了猶予中」は合わせて読めます。一方、後で「自動終了が有効な場合にだけ lifecycle が作られ」と設定条件が出るので、冒頭のケースは自動終了が有効なのだと補って読みました。冒頭にその条件を一言入れると、一般動作と今回の設定の区別がさらに明確になります。

## 一件の open と状態の再構成

説明の一件を、予約 ID を L、取得後の PR ID を P、ブラウザー文書 ID を B として再構成できます。B は評価上の略記です。

1. runtime は最後の画面を失い、終了猶予中だが受付可能。CLI は PR 指定、cwd、port を socket へ渡し、内部操作 `viewer.open` が登録済み `openViewer` を呼ぶ。既存 runtime が応答するため、新しい worker は使わない。
2. handler は PR 取得の `await` より先に予約する。runtime が一時 UUID の L を作り、lifecycle の `pendingViewers` に L と `{ phase: "opening" }` が保存される。L と PR ID は別物。
3. opening には deadline がない。今回のように接続済み viewer がなく、残る予約が opening だけなら、期限候補がなくなり既存の終了猶予タイマーが消える。pending があるので、空状態からの終了タイマーも始まらない。
4. `openPullRequest(reference, cwd)` が repository を確認し、利用可能な保存済み PR と Git object を使うか、GitHub から取得して同期する。この間、L は opening のまま。成功で PR の情報が返り、その `id` が P になる。
5. handler は同じ L を arm する。予約は startup になり、この時点の現在時刻に既定の 30 秒を足した期限を持つ。PR 取得の所要時間は、この 30 秒から差し引かれない。
6. handler は P と L を含む URL を返す。CLI が受け取りブラウザーを開く。ここでは予約 L はまだ残っている。
7. ブラウザーの viewer-session が URL の `viewerLease` を読み、表示 URL から取り除いてメモリーに保持し、別の文書 ID B を作る。`viewerHeartbeatRequest()` は B を `x-rvw-viewer-id`、L を `x-rvw-viewer-open-lease` に入れる。
8. App の定期問い合わせがこのヘッダーを `/api/meta/change-sequence` に付け、api helper が `RequestInit` を fetch に渡す。HTTP route は二つの ID を検証し、`heartbeat(B, L)` へ渡す。
9. heartbeat が L を `pendingViewers` から消し、B と現在時刻を `viewers` に保存する。変更通知番号を返す通信が、同時に画面の存在を記録する。これが説明上の終点。

この再構成では、PR の指定から P への変化、L の保存先と期限の変化、L の URL からヘッダーへの移動、最後に B の通信記録へつながるところを区別できました。「同じ予約」「これは PR の ID と別の値」「URL から消したことは、サーバーの予約を消したことではありません」が、一件を見失わないために効いています。

## 各観点の評価

### 入口の文脈

コマンドの用途、二つの用語、発生タイミング、成功を仮定する範囲が揃っています。「実行記録ではありません」も、説明用のケースを実測値として読まないために役立ちます。database が何を区別するのかはまだわかりませんが、同じプロセスを再利用できる前提として読むだけなら支障はありません。

### ケースと状態の連続性

最も強い箇所です。予約の作成、期限の付与、URL への搭載、ブラウザー側の保持、最初の通信での削除が同じ L として繋がります。終点を「URL の作成だけでもブラウザー起動の成功だけでも、ここまで到達したことは証明しません」と定めるため、操作成功と接続記録の成立を混同しません。

少し補ったのは、開始時にほかの pending がないことです。冒頭の条件一覧にはなく、後の「今回のように最後の画面が閉じ、残るものが opening だけなら」で今回の状態として確定しました。先の段落を読み直す必要はありませんでしたが、初期状態の条件は二箇所に分かれています。

### コード参照を開く理由

「PR を取得する `await` の前後に注目」「その `reserveViewer` へ UUID が渡ること」「渡された `RequestInit` をそのまま fetch に使い」など、何を確認するのかが参照の周囲に書かれています。ファイル紹介の列挙ではなく、直前の疑問を確かめる参照として読めます。

`open-handler` の再登場も、最初は順番、後では URL、最後は catch と観点が変わるため納得できます。既定値だけの参照は小さいものの、30 秒の出所を確認したい場合には目的が明確です。テストについても、呼び出し順の検査と `await` の直接確認を分けているので、順番の assertion だけから非同期の完了待ちまで証明されたとは読みません。

### モジュール・表現・非同期処理をまたぐ受け渡し

PR 取得の `await` と、その後にしか arm しない依存関係は明瞭です。後半は `URL → メモリー → ヘッダー → RequestInit → fetch → HTTP route → heartbeat` の各段に具体的な値があり、特に理解しやすい部分です。

socket の往路は送信と受信の参照がありますが、handler の戻り値が socket の応答になり CLI の受信へ戻る過程は、一連の記述から通常の要求・応答として補いました。本文は URL が CLI に返ることを明言しているため大きな空白ではありません。ただ、転送の形式、途中の timeout、エラー伝達の仕方までは再構成できません。

### 条件を変えた派生ケース

「URL は返ったが最初の通信が届かない」は主ケースの接続成功だけを変えているので比較しやすいです。L は startup に残り、期限処理で消え、ほかの記録がなければ終了猶予に入る、と追えます。遅延タイマーによる延長も、単純な 30 秒停止という読み違いを防ぎます。

PR 取得失敗は await の成功条件を変え、URL 作成に達せず catch で予約を取り消す。stopped のケースは到着時点を遅くし、予約を受理できるという初期条件そのものを変える。この三つは別々の条件変更として区別できます。最後の再試行ループは内容を説明しきっていませんが、「そこで切り替えてください」と別の読み始めを示しており、主ケースがそのまま続くようには見えません。

### 変更条件からの予測と確認先

PR 取得が 45 秒かかるように変更しても、その処理と socket 通信が継続して最終的に成功するという条件なら、L はその 45 秒の間 opening として残り、予約の接続待ち期限によっては失われないと予測します。arm の時点から startup の 30 秒が始まり、その 5 秒後に最初の有効な heartbeat が届けば L が消え、B が `viewers` に記録されるはずです。

確認先は `reservation-phases` の期限なし保存と arm、`schedule-reservations` のタイマー選択、`open-handler` の await と arm の順、`heartbeat-record` の記録更新です。`opening-test` は arm 前に設定時間を大幅に越えても残るという予測の補助になります。socket や PR 取得自体に別の期限がないとは本文から言えないので、45 秒かかる実際の open 全体が必ず成功するとは予測できません。

### 動作・データ・依存関係の具体性

「opening は期限なし」「startup は `Date.now()` に `startupTimeoutMs` を加える」「`pendingViewers` から消し、ブラウザー ID と現在時刻を `viewers` に入れる」が、用語を実際の変化に結びつけています。lifecycle という名前を知らなくても、その後の記述から保存する値と終了判断の関係を理解できます。

例外は図の前の「`RunningServer` の薄い転送は省略しています」です。RunningServer は初出で、それが runtime とどう異なり、どの矢印の間に入るものかは説明されていません。図の省略を理解するためだけに新しい名前を覚えることになり、初読にはあまり役立ちません。転送を省いたことだけ示すか、予約の窓口との対応を一言添える方が自然です。

## 推測した箇所と残る問い

- 冒頭の runtime は自動終了が有効だと、後の条件から補いました。無効な場合の予約 API の振る舞いは不明です。
- 初期状態にほかの pending がないことは、タイマー説明で追加された条件として受け取りました。
- handler から CLI への URL の戻り道は socket の応答だと補いました。成功値をどう返すか、途中で待機を打ち切る条件は本文からはわかりません。
- `RunningServer` は予約の窓口と lifecycle の間にある転送層らしいと推測しましたが、正確な位置は未確定です。

終点以降については推測せず、次の問いを残しました。メモリーに保持した L は二回目以降の定期問い合わせでも送るのでしょうか。送るなら、既に消費された L を heartbeat はどう扱うのでしょうか。また、最初の問い合わせが起動直後なのか、定期実行の初回まで待つのかは不明です。これらは「最初の通信が届いた」地点までの理解を妨げませんが、30 秒以内に到達する条件や継続中の状態を調べるなら `browser-poll`、`browser-lease`、`heartbeat-record` を開きたいです。

## 範囲と長さ

startup の開始時点だけで終わらず、URL に載った予約が最初の通信で消えるまで追う長さには価値があります。これがあるため、何を待つための 30 秒なのか、予約が PR ID とも文書 ID とも違う理由が具体的になります。PR 取得の内部説明も、await が実際の取得・同期を含むことを理解するのに十分な短さです。

図は期限の付く境界だけに範囲を絞っていることが明記されており、本文との重複が整理として働いています。一方、arm の説明と URL への移動の間に長めのテスト説明が入るため、状態の流れが一度止まります。テストの段落を最初の heartbeat の後へ移すと、一件をより連続して読めそうです。

末尾の stopped と再試行ループは今回の初期条件の限界を示す価値がありますが、主題との距離は最も大きい部分です。全体を短くするなら、具体的な再試行入口の案内を圧縮し、URL から heartbeat までの受け渡しは残したいです。全体として、長さの大部分は一件の状態をつなぐために使われています。
